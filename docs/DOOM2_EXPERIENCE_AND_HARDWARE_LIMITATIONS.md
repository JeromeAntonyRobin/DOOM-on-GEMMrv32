## 2. Root Cause Analysis of Current Display Glitches

### A. The "Vertically Squished Top Half" Glitch
* **Observed Symptom**: The rendering is confined to the top half of the CRT/monitor, vertically crushed into roughly 120 lines, while the lower portion remains black or unupdated.
* **Root Cause 1 (Legacy 120-line Firmware Execution)**: 
  The existing DOOM firmware (`v2` or earlier compiled binaries) was compiled for $160 \times 120$ resolution (120 active scanlines). When executed on the upgraded 320x200 4bpp hardware:
  - The software only iterates $y \in [0, 119]$ (120 scanlines).
  - Out of the 200 scanlines generated by the hardware raster scanner, lines 120 to 199 are never touched by the CPU, leaving the bottom 40% completely unrendered.
* **Root Cause 2 (Perspective Focal Length & Fixed-Point Overflow)**:
  In `r_segs.c`, projection calculations used:
  ```c
  int x1 = CENTER_X + FROM_FIXED(FIXED_DIV(tx1 * FOCAL_LEN, tz1));
  ```
  Where `tx1` is 16.16 fixed-point (e.g. $200 \times 65536 = 13,107,200$). Multiplying by `FOCAL_LEN` (160) yields $2,097,152,000$, which exceeds the 32-bit signed integer limit ($2,147,483,647$) when `tx1 > 163`. This arithmetic overflow wraps into negative numbers, collapsing wall projection heights towards `CENTER_Y` and clamping vertices to the top viewport edge.

### B. The "Horizontal Line Breaks" & Pixel Noise Glitch
* **Observed Symptom**: Sprites and wall surfaces are fragmented by horizontal line breaks and speckles.
* **Root Cause 1 (Port A VRAM Read-Back Byte Lane Steering)**:
  In `rtl/core/neorv32_vga.vhd`, Port A read-back was implemented as:
  ```vhdl
  bus_rdata_o(7 downto 0) <= vram_rdata_a;
  ```
  In 32-bit RISC-V architectures, when the CPU executes `lbu` (Load Byte Unsigned) to an unaligned byte address:
  - Address ending in `"00"` expects data in `bus_rdata_o(7 downto 0)`.
  - Address ending in `"01"` expects data in `bus_rdata_o(15 downto 8)`.
  - Address ending in `"10"` expects data in `bus_rdata_o(23 downto 16)`.
  - Address ending in `"11"` expects data in `bus_rdata_o(31 downto 24)`.
  Because `vram_rdata_a` was only connected to bits `(7 downto 0)`, any read to byte offsets 1, 2, or 3 returned `0x00`. When `put_pixel_4bpp` executed a read-modify-write (`vram[byte_idx] = (vram[byte_idx] & 0xF0) | (col & 0x0F)`), 75% of pixel writes inadvertently zeroed out the neighboring pixel, creating horizontal slits and speckles across every scanline.
* **Root Cause 2 (8bpp vs 4bpp Memory Format Mismatch)**:
  When legacy 8bpp code writes a single byte per pixel into the newly configured 4bpp framebuffer (where 1 byte holds 2 packed pixels), every byte write overwrites two adjacent pixels with an un-remapped 8-bit index, causing 2x horizontal compression and color channel distortion.

## 3. Physical Hardware Hindrances of Digilent Basys 3

| Hardware Metric | Digilent Basys 3 Spec | Authentic Id Software DOOM 2 Requirement | Deficit / Hindrance |
| :--- | :--- | :--- | :--- |
| **FPGA Chip** | Artix-7 `XC7A35T-CPG236-1` | 486 DX2-66 / Pentium | Compute capable (50 MHz RISC-V) |
| **External RAM** | **0 MB (None on board)** | **4 MB to 8 MB RAM** | **-4 MB Deficit** (No external RAM) |
| **Internal Block RAM** | 50 BRAM36 tiles (**225 KB total**) | 4 MB Zone Memory (`Z_Init`) | **94.4% Memory Shortfall** |
| **Current BRAM Budget** | 48 / 50 BRAMs utilized (96%) | IMEM + DMEM + VRAM | Only 2 BRAMs remaining |
| **Onboard SPI Flash** | 4 MB (`Macronix MX25L3273F`) | `DOOM2.WAD` = **14.6 MB** | **-10.6 MB Deficit** (WAD exceeds Flash) |
| **Flash Usable Margin** | Bitstream = 1.4 MB $\rightarrow$ **2.6 MB free** | Shareware `DOOM1.WAD` = 4.2 MB | Full WAD cannot fit in SPI Flash |

### The Core Architectural Dilemma
1. **The Zone Memory Trap**: Id Software's authentic engine relies on `Z_Malloc` dynamic heap allocation, loading entire BSP nodes, subsectors, segs, linedefs, textures, patches, and sound effects into RAM simultaneously.
2. **The WAD Storage Trap**: A complete, unmodified `DOOM2.WAD` is 14.6 MB. The Basys 3 board only has a 4 MB SPI flash chip, of which 1.4 MB is occupied by the FPGA bitstream.

## 6. Detailed Roadmap to Deliver the True DOOM 2 Experience

### Phase 1: Fix Display Hardware & Bus Subsystem (Immediate)
1. **Replicate Read-Back across All Byte Lanes in `neorv32_vga.vhd`**:
   Connect `bus_rdata_o(31 downto 0) <= vram_rdata_a & vram_rdata_a & vram_rdata_a & vram_rdata_a;` so all CPU `lbu`/`lb` byte reads return valid pixel data regardless of address alignment.
2. **Synchronize VGA Pipeline & Counters**:
   Align the sync pulse delays and scanout pipeline strictly to the `pclk_tick` pixel domain, eliminating horizontal jitter and pixel phase distortion.
3. **Full 200-Line Aspect Ratio Centering**:
   Ensure the active video spans all 200 native scanlines centered in standard 480p VGA timing.

### Phase 2: Authentic DOOM 2 Game Engine (`DOOM2-BareMetal`)
1. **Authentic `MAP01: Entryway` Data Structures**:
   Direct conversion of original DOOM 2 MAP01 binary lumps (NODES, SECTORS, LINEDEFS, SIDEDEFS, VERTICES) into indexed, read-only flash/ROM structures.
2. **Genuine DOOM 2 Weapon System**:
   Implement the **Super Shotgun (SSG)**:
   - 8-gauge double-barrel blast (20 pellets, hitscan spread cone).
   - Authentic 4-state reload animation sequence (fire, open barrels, insert shells, snap shut).
3. **DOOM 2 Monster Roster & Finite State Machines**:
   - Former Human Sergeant (Shotgunner): Hitscan attack, drop shotgun.
   - Imp: Ranged fireball projectile with explosion burst.
   - Pinky Demon: Fast pathfinding, melee bite.
4. **Visplane & Seg Rendering Engine**:
   - Visplane span-buffering for authentic textured ceilings and floors.
   - 1D screen clipping arrays (`floorclip` and `ceilingclip`) to guarantee zero overdraw.
5. **Authentic DOOM 2 Status Bar**:
   - Authentic Doom status bar background plate.
   - Animated Doomguy face with directional gaze, evil grin on weapon fire, and bloodied states for low health.
